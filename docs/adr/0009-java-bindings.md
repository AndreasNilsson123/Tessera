# ADR 0009: Java bindings - JNI baseline, FFM on Java 22+, one multi-release jar
Status: accepted (Phase 7). Replaces ADR 0002 ("proposed").

**Both bindings, one interface.** The C API is wrapped by a small `NativeApi` interface with two implementations: JNI (works on Java 11+, which is where most LWJGL users are) and `java.lang.foreign` (final since Java 22). The public classes (`Context`, `ContextConfig`, ...) only ever see `NativeApi`. `-Dtessera.binding=auto|jni|ffm` selects; auto means FFM on Java 22+ when it can be set up, otherwise JNI, and says why in `Natives.fallbackNote()`. Verified on Java 17 and 21 (JNI) and 22, 25 and 28 (FFM), from the same jar. Java 19/20 run the JNI path (their Panama is a preview API and is ignored).

**One native file for both.** The JNI glue (`bindings/java/src/jni`) is compiled *into* the tessera shared library, so JNI loads it with `System.load` and the FFM binding just `dlsym`s the same C API out of the same file. Nothing to keep in sync, one thing to embed in the jar. It is optional at build time (`-DTESSERA_BUILD_JAVA=ON`), so the core library gains no JNI dependency by default.

**FFM is hand-written, not `jextract`ed.** The C API is ~20 functions plus two structs; hand-written bindings are a few hundred reviewable lines, need no tool in the build, and the struct layouts are pinned by explicit offsets and by an ABI-version check at load time (`Natives.EXPECTED_ABI`). `jextract` was not installed, and generated bindings for this surface would be larger than the thing they wrap.

**Packaging.** A multi-release jar: Java 11 classes at the root (including the JNI binding and the embedded native library under `natives/<os>-<arch>/`), the FFM binding under `META-INF/versions/22`. `FfmNativeApi` is deliberately package-private: the `jar` tool rejects a versioned directory that adds a *public* class with no base counterpart. Built with plain `javac`/`jar` driven by CMake (no Maven/Gradle). Package name `dev.tessera` is a placeholder; rename it before publishing.

**Native library loading.** `-Dtessera.library.path` wins; otherwise the embedded copy is written to a fresh private temp directory (`Files.createTempDirectory`, 0700 on POSIX), verified against the checksum of the embedded bytes, and loaded by absolute path with `System.load` (never `System.loadLibrary` and its search path). A fresh directory per run means a pre-planted file can never be what gets loaded. JNI lets a library be loaded by only one classloader; a second classloader that asks gets its own private copy (independent native state) instead of an `UnsatisfiedLinkError`. Tested: two isolated classloaders each use the library concurrently. The FFM binding has no such restriction and shares one instance.

**Java semantics chosen deliberately.**
- *Errors:* programming errors (wrong thread, closed context, invalid handle, not initialised) are `IllegalStateException`; environmental failures are `TesseraException` carrying the native `Result` and the native message; loss is `ContextLostException`.
- *Virtual threads are refused* for `makeCurrent`: they can migrate between OS threads between two calls, and a GL context belongs to exactly one. (Detected by reflection so the code still compiles and runs on Java 11.)
- *`Cleaner` is a safety net, not a plan.* It works at all only because Phase 6 made destroying a context held by another thread legal (a Cleaner thread cannot know where the render thread is).
- *Holder-exit tolerance.* `Thread.join()` returns when the Java thread has terminated, but its OS thread is still finishing, and the native library releases a context a thread left current only when that OS thread really exits. A `makeCurrent` that fails with `WRONG_THREAD` while the last known holder is a dead thread therefore retries for up to two seconds instead of reporting a conflict that is about to disappear. (Found by the first Java run; the C++ tests join OS threads and could not show it.)
- *Lifecycle.* Creating a context initialises the library once, implicitly; a shutdown hook first stops native log callbacks into the JVM, then terminates the library. Explicit `init()/terminate()` stack on top. A JVM exiting with live contexts, one of them current on a parked thread, exits in under a second (tested on every JDK).

**Logging crosses threads.** The native log callback can fire on threads the JVM has never seen (Tessera's own). The JNI trampoline attaches as a daemon, calls a static Java method, clears any exception, and detaches; the FFM upcall catches `Throwable` (an exception escaping an upcall crashes the JVM). The class reference taken by the JNI glue is deliberately never released: a callback running on another thread may still be using it. Strings handed to the JVM are forced to printable ASCII first (`NewStringUTF` on malformed modified-UTF-8 is undefined behaviour, and GL strings come from drivers).

**LWJGL.** `TesseraFunctionProvider` (an `org.lwjgl.system.FunctionProvider`) and `TesseraGL`. LWJGL's `GL` class loads the system OpenGL library the instant it is first touched unless `Configuration.OPENGL_EXPLICIT_INIT` is set, so a custom provider can only be installed if that flag is set first; `TesseraGL.install()` does so, and says exactly that if it is too late. LWJGL keeps one provider per classloader, so Tessera's cannot be mixed with LWJGL's own GLFW/system OpenGL in the same classloader.

**Test dependencies** (LWJGL, JavaFX) are never vendored: `scripts/fetch-java-deps.py` downloads pinned versions from Maven Central into the git-ignored `third_party/java/`, verifying each file's SHA-1 against the one Maven Central publishes. Tests that need them are skipped when absent.
